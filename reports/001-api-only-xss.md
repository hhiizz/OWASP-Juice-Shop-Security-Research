## 1. 漏洞摘要

本次測試透過檢視前端 `main.js`，發現應用程式使用 `/api/Products/` 商品 API。接著修改 HTTP 請求，測試該 API 支援的請求方法，發現除了讀取商品資訊外，也能透過 `PUT` 更新商品資訊。

進一步測試發現，商品更新 API 未有效檢查 Bearer Token 所代表的使用者是否具有管理員權限，使非管理員使用者也能竄改商品資訊。此問題涉及伺服器端授權檢查缺失。

本報告以三星「API-Only XSS」挑戰為主題。官方將此挑戰定義為透過 API 植入儲存型 XSS；目前提供的實測紀錄涵蓋 API 發現與未授權商品更新，尚未提供 XSS payload、儲存結果、前端觸發位置與執行證據，因此尚不宣稱已完成 XSS 驗證。[官方挑戰說明](https://pwning.owasp-juice.shop/companion-guide/latest/part2/xss.html)

## 2. 測試環境與前置條件

- 測試對象：OWASP Juice Shop 實驗環境。
- 實際版本、部署方式、網址與工具版本：待補，參見 [環境紀錄](../environment/README.md)。
- 權限測試情境：使用非管理員身分的 Bearer Token 發送商品更新請求。
- 目標商品 ID、實際修改欄位與原始內容：待補。
- 觀察結果來源：研究者提供的操作描述；本報告撰寫時未連線至實驗環境重跑測試。

## 3. 發現過程

### 3.1 從 main.js 發現商品 API

檢視前端載入的 `main.js`，搜尋與商品資料相關的程式碼，發現 `/api/Products/` 路徑，據此辨識出商品 API 的入口。

這項發現提供了後續測試方向。API 路徑出現在前端程式碼中本身並不構成漏洞；安全性仍需由伺服器端的身分驗證與授權機制保障。

### 3.2 修改請求方法，確認支援 PUT

取得商品相關請求後，修改 HTTP 請求方法並調整請求內容，發現商品 API 支援 `PUT`，可用於更新商品資訊。

實際發送更新請求後，觀察到商品內容被修改，確認此 API 暴露了商品寫入能力。API 支援 `PUT` 本身屬於功能設計；問題在於未限制哪些使用者可以執行商品更新。

### 3.3 發現缺少管理員權限檢查

在非管理員使用者情境下發送更新請求，仍可修改商品資訊，顯示 API 沒有有效限制商品管理權限。

此處需區分兩種檢查：

- **身分驗證**：Bearer Token 是否有效，以及代表哪個使用者。
- **授權檢查**：該使用者是否具有管理商品的權限。

目前結果支持「非管理員也能更新商品」的授權缺失。是否完全不驗證 Token，仍需另外測試不帶 Token、無效 Token 與過期 Token 的情境，不能僅由一般使用者可修改商品就推論。

## 4. 重現流程

以下流程整理自研究者描述；完整原始請求與回應待補。

1. 登入一般使用者帳號，確認該帳號不具有管理員權限。
2. 檢視前端 `main.js`，找到 `/api/Products/` 商品 API。
3. 取得目標商品資料，保存修改前的內容。
4. 將商品請求改為 `PUT`，指定目標商品，於請求本文放入欲修改的商品資訊。
5. 使用一般使用者的 Bearer Token 發送更新請求。
6. 重新讀取商品資料，比對修改前後的欄位，確認更新是否已儲存。

### 請求格式示意

下列為整理報告用的示意請求，並非實際封包。`<product-id>`、Host、Token 與欄位應以實測內容替換；`description` 僅作為商品資訊欄位的例子。

```http
PUT /api/Products/<product-id> HTTP/1.1
Host: <lab-host>
Authorization: Bearer <regular-user-token>
Content-Type: application/json

{
  "description": "API update verification marker"
}
```

**預期行為：** 若商品更新僅限管理員，伺服器應拒絕一般使用者的修改請求，商品內容維持原值。

**實際觀察：** 依研究者描述，非管理員使用者仍能透過 `PUT` 修改商品資訊。實際 HTTP 狀態碼、回應內容與修改前後比對資料尚待補充。

## 5. API-Only XSS 的後續驗證

商品資訊可被修改提供了潛在的 XSS 寫入入口，但純文字修改成功尚不足以證明 XSS。要確認儲存型 XSS，還需要證明輸入被保存，且在其他使用者瀏覽相關內容時，被當作可執行內容處理。

官方挑戰使用以下 payload；此處列為後續實驗參考，並非宣稱研究者已使用或成功觸發：

```html
<iframe src="javascript:alert(`xss`)">
```

此 payload 與挑戰要求來自 [官方 XSS 挑戰說明](https://pwning.owasp-juice.shop/companion-guide/latest/part2/xss.html)。

後續需補充：

- 實際注入的商品欄位與完整 `PUT` 請求。
- 更新後重新讀取商品的結果，確認 payload 是否持續存在。
- 實際呈現該欄位的頁面、觸發操作與瀏覽器執行證據。
- 是否影響其他使用者，以及挑戰完成畫面（如有）。

## 6. 成因分析

依目前觀察，商品更新介面缺少有效的伺服器端管理權限檢查，讓不具備商品管理權限的使用者也能執行更新。若商品維護是管理員功能，這代表一般使用者可以越過原本的權限邊界。

目前未取得對應測試版本的後端程式碼，尚不能判定缺少哪個 middleware、Token 是否完全未驗證，或是否存在其他設定錯誤。

XSS 部分仍需確認資料儲存與呈現流程。若商品欄位被當作 HTML 輸出且未適當處理，可能使寫入內容形成儲存型 XSS；實際渲染位置與防護缺失尚待驗證。

## 7. 影響與風險評估

| 發現 | 目前證據與限制 |
| --- | --- |
| 商品內容可遭非管理員修改 | 依研究者實測描述記錄，原始封包與前後比對待補 |
| Token 缺少管理員權限檢查 | 一般使用者情境可更新商品；需補充角色與權限佐證 |
| 未登入或無效 Token 也可更新商品 | 尚未提供測試結果 |
| 可修改其他商品或其他欄位 | 尚未提供測試結果 |
| 儲存型 XSS | 尚未提供 payload 儲存與瀏覽器執行證據 |

商品竄改可能破壞商品資料的完整性。若後續確認可植入並觸發儲存型 XSS，則還可能影響瀏覽該內容的使用者，實際影響需依執行環境、可接觸的資料與權限評估。

三星為挑戰難度，並非漏洞嚴重程度。本報告目前不給定 CVSS 分數。

## 8. 修補建議

1. **驗證身分並檢查管理權限。** 在商品更新端點驗證 Token 的有效性，再依伺服器信任的身分與權限資料，確認使用者是否可管理商品；僅持有有效 Token 不代表具備商品更新權限。[OWASP 授權防護建議](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
2. **限制可修改欄位。** 依業務需求建立允許更新的欄位清單，驗證資料型別、長度與格式，避免直接將整份請求本文套用至資料模型。
3. **安全呈現商品內容。** 純文字欄位應使用文字輸出或依輸出情境編碼；若確實需要 HTML，應採用持續維護的 HTML sanitizer 與允許清單，避免繞過前端框架的安全處理。[OWASP XSS 防護建議](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)
4. **縮減介面與保留紀錄。** 不需要的寫入方法應關閉；合法商品更新應保留操作者、目標商品與變更內容，以利追蹤。

以上為修補建議，尚未實作或驗證。
